## 2. 특이사항 및 비고

### 2.1 특이사항 (결과 해석 시 반드시 같이 읽을 제약)

1. **closed 부하 모델**: JMeter 스레드는 응답을 받아야 다음 요청을 보낸다. 서버가 느려지면 요청률이 스스로 줄어 과부하가 실제보다 덜 보일 수 있다 (coordinated omission).
2. **인증**: 카카오 OAuth는 테스트 대상에서 제외한다. staging 한정 부하테스트 전용 로그인 통로로 세션을 발급하므로, **로그인(OAuth) 성능은 측정하지 않는다.**
3. **데이터**: 합성 회원 3,000명 (seed 2535, density medium). 실제 회원 분포·조건과 다르다.
4. **정적 리소스**: 이미지·CSS·JS는 요청하지 않는다. HTML/JSON 응답 성능만 측정한다.
5. **환경 공존**: 단일 VM에서 prod와 staging이 같은 CPU를 나눠 쓴다. 테스트는 prod 미사용 시간대에 수행한다.
6. **네트워크**: 부하 발생기↔서버 왕복 시간(RTT)이 응답시간에 포함된다. TODO: RTT __ms, 부하 발생기 위치 __
7. **가정값**: 사용자 유형 비율과 행동 주기(7절)는 가정이다. 실제 접속 로그가 쌓이면 보정한다.

### 7.3 TPS 산출

공식: **TPS ≈ 인원 ÷ 주기(응답시간 + 생각 시간)** (Little의 법칙)

| ID | 단위업무 | 산식 | 목표 TPS |
|---|---|---|---|
| B1 | 매칭 리스트 조회 | 162 ÷ 30초 | 5.40 |
| B2 | 프로필 상세 조회 | 162 ÷ 30초 | 5.40 |
| B3 | 좋아요 | B2 × 30% | 1.62 |
| C1 | 대화 시작 | 108 ÷ 1,800초 | 0.06 |
| C2 | 채팅 폴링 | 108 ÷ 3초 | 36.00 |
| C3 | 메시지 전송 | 108 ÷ 20초 | 5.40 |
| C4 | 대화 목록 조회 | 108 ÷ 120초 | 0.90 |
| | **합계** | | **54.78 ≈ 55 TPS** |

### 7.4 임계치 기준

| 단계 | 동시 사용자 | 환산 TPS |
|---|---|---|
| 50% | 135명 | 약 27 |
| 100% (목표) | 270명 | 약 55 |
| 150% | 405명 | 약 82 |
| 200% | 540명 | 약 110 |
| 300% | 810명 | 약 164 |

**임계점(knee)** = 단계를 올리는 중 처음으로 6절의 응답시간 또는 오류율 목표를 넘기는 단계.

### 7.5 사전 추정 (검증 전 가설)

- 폴링(C2)이 전체 TPS의 약 **66%**를 차지한다. 개별 요청은 가볍지만 양이 많아서, 폴링 방식 자체가 부하의 주된 원인일 수 있다.
- 필요 CPU = TPS × 요청당 서비스 시간. 요청당 10 / 20 / 30ms로 가정하면 각각 약 **0.55 / 1.10 / 1.65코어**다. 이 VM은 1 OCPU(2 vCPU, 하이퍼스레드)라 실효 성능이 2코어에 못 미치므로, **목표 부하에서 CPU 여유가 빠듯할 가능성**이 있다 (H8).
